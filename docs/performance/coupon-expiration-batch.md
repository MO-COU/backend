# 이벤트 쿠폰 만료 배치 성능 검증

## 결론

- 만료 후보 조회는 `ORDER BY expires_at, coupon_issue_id`를 사용한다.
- 기본 청크 크기는 **2,000건**으로 설정한다.
- 이 결론은 이벤트 만료 배치를 단독 실행한 결과다. 사용 요청이 대량으로 겹치는 운영 조건에서는 1,000건과 5,000건을 동시 부하로 다시 측정한다.

## 평가 대상과 범위

이 문서는 이벤트 쿠폰 만료 배치의 처리량과 정합성을 검증한다.

| 구분 | 값 | 의미 |
| --- | ---: | --- |
| 이벤트 쿠폰 재고 | 10,000장 | 발급 성공의 최대치 |
| 이벤트 만료 대상 | 10,000건 | 배치가 직접 처리하는 최대 행 수 |
| 발급 부하 | 사용자 20,000명, 60초 램프업 | 발급 API의 별도 동시성·부하 테스트 범위 |

이 측정의 로컬 DB는 이벤트 쿠폰 발급 성공분 10,000건과 그 최초 이력만 가진다. 회원 20,000명의 60초 램프업은 재고 상한에 의해 최대 10,000건만 발급 성공하는 별도 발급 부하 시나리오이며, 만료 배치의 직접 처리량에는 포함하지 않는다.

만료 배치는 60초 간격으로 실행된다. Spring의 `fixedDelay` 방식이므로 이전 실행이 끝난 뒤 다음 실행까지 60초를 기다리며, 동일 애플리케이션에서 배치 실행이 겹치지 않는다.

## 정합성 규칙

만료와 사용은 모두 `ISSUED` 상태에서만 조건부 갱신한다.

| 상황 | 결과 |
| --- | --- |
| 만료 시각 이전에 사용 갱신이 먼저 성공 | `USED` 상태와 `USED` 이력만 남음 |
| 만료 갱신이 먼저 성공 | `EXPIRED` 상태와 `EXPIRED` 이력만 남음 |
| 만료 시각과 같은 DB 시각의 사용 요청 | 사용 조건이 `expires_at > CURRENT_TIMESTAMP`이므로 사용 불가 |
| 만료 이력 batch insert 실패 | 청크 트랜잭션 전체 롤백, 상태는 `ISSUED` 유지 |

만료 후보를 먼저 조회한 뒤에도 `UPDATE ... WHERE status = 'ISSUED'` 결과가 1인 행만 `EXPIRED` 이력 batch insert에 포함한다. 따라서 경쟁에서 사용 전이가 승리한 행에는 만료 이력이 생성되지 않는다.

## 실행계획

조건은 `status = 'ISSUED' AND expires_at <= '2026-08-19 00:00:00'`, `LIMIT 1,000`이다. MySQL 8.0.46에서 측정했다.

| 후보 정렬 | 실행 방식 | 실제 시간 | 해석 |
| --- | --- | ---: | --- |
| `coupon_issue_id` | 만료 후보 10,000건을 읽고 ID 정렬 후 1,000건 반환 | 약 5.13ms | 매 청크에 불필요한 정렬 발생 |
| `expires_at, coupon_issue_id` | `idx_issue_status_expires(status, expires_at)` 범위/커버링 스캔으로 1,000건 반환 | 약 0.36ms | 정렬 없이 필요한 후보만 반환 |

후보 조회는 배치의 전체 시간 대부분을 차지하지는 않지만, 반복되는 불필요한 정렬을 제거하므로 두 번째 정렬을 유지한다.

## 청크 측정

- 측정일: 2026-08-19, Asia/Seoul
- DB: 전용 `mocou_perf`, MySQL 8.0.46
- 방식: 각 청크에서 워밍업 1회 후 측정 3회. 실행마다 이벤트 데이터만 초기화했다.
- 시간: 애플리케이션 기동 시간이 아닌 `couponExpirationStep` 실행 로그의 step 시간이다.
- 검증: 매 실행 후 이벤트 쿠폰의 `EXPIRED` 상태와 `EXPIRED` 이력이 각각 10,000건인지 확인했다.

| 청크 | 측정 1 | 측정 2 | 측정 3 | 중앙 시간 | 중앙 처리량 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 500 | 13.918초 | 14.870초 | 15.091초 | 14.870초 | 672.49건/초 |
| 1,000 | 13.807초 | 14.162초 | 14.173초 | 14.162초 | 706.11건/초 |
| 2,000 | 13.920초 | 14.149초 | 14.547초 | 14.149초 | 706.76건/초 |
| 5,000 | 15.015초 | 15.124초 | 16.471초 | 15.124초 | 661.20건/초 |

2,000건은 중앙 처리량이 가장 높았고, 1,000건보다 완료 시간이 0.013초 짧았다. 차이는 사실상 미미하지만 5,000건보다 중앙 처리량이 약 6.9% 높아 기본값으로 선택했다.

## 한계와 재측정 조건

이번 결과는 만료 배치와 사용 요청이 대량으로 겹치지 않는 이벤트 흐름을 전제로 한다. 발급 램프업은 쿠폰 발급 시점의 부하이고, 만료 배치는 유효기간 종료 후의 작업이므로 일반적으로 서로 다른 시간대에 실행된다.

다음 조건이 운영 요구사항에 포함되면, 1,000과 5,000을 대상으로 사용 요청 동시 부하를 넣어 다시 측정한다.

- 만료 배치가 실행되는 동안 사용 요청이 지속적으로 유입되는 경우
- 행 잠금 대기 시간 또는 사용 API 지연 시간을 성능 기준에 포함하는 경우
- 이벤트 만료 대상이 10,000건을 초과하도록 정책이 바뀌는 경우
